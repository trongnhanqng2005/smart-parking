# Flyway migrations

`V1__create_approved_schema.sql` is the baseline migration for the approved 38-table ERD. V2 applies the approved `residents.email` width correction; V3 materializes the approved authentication/RBAC schema decisions. V4 (`db.migration.V4__apartment_resident_normalized_identity_and_lifecycle`) is a Java-based migration for AHR-01's canonical Unicode backfill/preflight and additive persistence decisions. It has a pinned custom checksum and runs non-transactionally because MySQL DDL implicitly commits. V5 (`db.migration.V5__vehicle_right_pending_transitions`) is a checksummed, non-transactional AHR review-remediation migration; its preflight rejects guarantor-shape rows that the corrected V5 CHECK cannot allow, then it replaces the guarantor CHECK and adds vehicle-owned pending-transition storage. AHR-11 uses V4's existing table-specific `VOID` literals and lifecycle metadata; it has no schema migration. Canonical transforms and binary-key behavior are documented in `docs/database/data-dictionary.md` and `docs/database/database-overview.md`. Future reviewed migrations use the next version after checking migrations already merged to `main`; coordinate version numbers across concurrent feature branches. Once applied to a database, a migration is immutable—make later changes in a new version.

Do not add empty migrations or edit an applied migration. Schema updates must preserve the approved ERD and its feature ownership; distinguish project-approved additions from original ERD fields in synchronized documentation. Migration history on the database is authoritative for applied versions. If V4 or V5 fails after any MySQL DDL, inspect both Flyway history and actual schema, reconcile to a consistent state before Flyway repair/retry, and never retry blindly.
